二、新版 MQTT 协议核心变化

当前服务端仍有旧协议痕迹

  • 人员下发 topic 仍使用 whitelist/upsert、whitelist/delete、whitelist/clear。
  • 柜格规划仍使用 lockerModel/upsert 和 binding/upsert。
  • 开柜/释放仍向 control.extra 发送 lockerId。
  • access 事件解析仍读 lockerId，没有使用 groupId + cabinetId。
  • 用户人脸字段仍用 face_image_url、face_image_md5 下发。

新版协议要求

  • 统一 topic 前缀：fitlock/v1。
  • 人员接口：user/upsert、user/delete、user/clear。
  • 柜格接口：cabinet/list、cabinet/upsert、cabinet/delete、cabinet/clear。
  • 柜格唯一标识：groupId + cabinetId，不再依赖 lockerId。
  • access 事件必须回执到 fitlock/v1/event/{uuid}/access_reply，且 serialNo 必须一致。

四、数据模型与数据库改造

  1. 柜格标识映射： 当前数据库 Locker.channelId 关联 DeviceChannel.id，Locker.portNo 是端口号。新版协议需要 groupId + cabinetId。 建议映射为：groupId = DeviceChannel.channelNo，cabinetId = Locker.portNo。这样不需要马上改表。
  2. 柜格显示名： lockerNo 当前有时是 1-1，有时可能是旧的业务 ID。下发新版协议时建议作为 cabinetName，不要再作为设备唯一 ID。
  3. 柜格状态： 新协议状态为 1=空闲, 2=占用, 3=锁定, 4=故障, 5=空格。当前注释里 3 写“禁用”，语义可映射为“锁定”，页面文案也要同步。
  4. 长期/临时绑定： 当前 Locker.bindEndTime 是 LocalDate，协议要 10 位秒级 endTimestamp。下发时使用当天 23:59:59 转秒，回传事件也要秒转本地时间。
  5. 用户字段： 新协议支持 phone 与 pin。当前后台有 phone，没有独立 pin 字段。若要支持密码开柜，需要新增用户 PIN 字段或明确复用某个字段，不建议复用登录密码。
  6. 门状态： 协议 Cabinet.doorOpen 当前数据库无字段。第一阶段可下发固定 0，如果要展示真实门状态，需要给 sys_locker 新增 door_open 并在事件中维护。
